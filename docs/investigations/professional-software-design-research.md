## 0. Window stability — investigated before the design analysis

**Conclusion: the source investigation is complete; real window stability remains unverified.** No specific symptom, reproduction steps, crash log, Windows build or prior stability report was available in this checkout. On continuation, CMake, Ninja and PySide6 6.7.3 were installed into an ignored local virtual environment, but the PySide wheel does not provide the Qt C++ development SDK and the host lacks required Qt runtime libraries (`libGL.so.1`, `libEGL.so.1`, `libxkbcommon.so.0`, `libdbus-1.so.3`). The existing Python QML helper failed on import due to `libGL.so.1`; it also uses substitute Python state objects rather than the production C++ backend. There is no native Windows desktop or debugger here. Consequently no production application was built or launched, no tests were run, and there is no basis to claim a crash, a fix, or a stable Windows release. The following are investigation leads, not diagnosed causes.

### Required completion gate for a real stability verdict

On a representative packaged Windows build, with version, Qt version, GPU/driver, display geometry/scaling, logs and exact steps recorded:

1. Start clean, resize repeatedly through minimum and large sizes, maximize/restore and minimize/restore; exit and relaunch. Compare saved normal bounds and maximized state with what was intended, including transitions while a dialog is open. Check for freezes, console/debug-output QML errors and geometry oscillation.
2. Open several documents; resize dock splitters, collapse/restore areas, float/redock/close panels and repeatedly save/reset a layout. Confirm the canvas, active document, selection and view do not unexpectedly reset; repeat with drawing and a tablet.
3. Move a floating panel to a second monitor, exit, disconnect that monitor, relaunch; repeat at mixed scaling and after display-resolution changes. Verify every panel is recoverable and visible or can be reset.
4. Exercise close with multiple modified tabs: save, discard, cancel, failed save and a stroke in progress. Force terminate after a known snapshot, restart and check what is offered and whether saved files remain untouched. Use disposable projects.
5. Repeat on at least one GPU-backed and one software-rendered configuration; capture a crash dump or call stack on failure. Run relevant local tests when dependencies are available, then perform the native test regardless of offscreen results.

**Stop condition:** do not attribute a reported window problem to the hypotheses above without reproducing it. Treat a reproducible freeze, crash, lost panel or lost artwork as a release blocker before visual work. This report does not resolve an unspecified real-world failure.

## 3. Why the strongest decisions work — and their costs

1. **Keep the active instrument and immediate state close.** CSP's tool/subtool/property sequence and Harmony's contextual Tool Properties reduce the need to hunt through a global preferences dialog. Krita's pop-up brings a small working set to the pointer. **Inference:** this reduces repeated travel and makes changes attributable to the active tool. **Cost:** hidden context can surprise users when a selection silently changes what a control edits. A persistent tool/preset name and focus cue are essential.
2. **Use progressive disclosure, not permanent omission.** CSP separates common properties from Sub Tool Detail; Krita exposes presets first and an editor for deeper behavior. **Inference:** novices can paint before learning brush engines, while experts retain control. Preserve a discoverable path to every advanced setting; do not require hover-only discovery or remove essential values merely to look clean.
3. **Treat the canvas as a shared working surface, not a decorative hero.** CSP collapses docks, Krita has configurable canvas-only mode and OpenToonz can maximize panes. **Inference:** they reclaim working area without requiring an artist to abandon their tools permanently. The right default density is contextual: a painter and an exposure-sheet editor need different amounts of canvas and grid.
4. **Make workspaces different views of the same work.** OpenToonz rooms retain the current scene; Harmony's views are purpose-specific; Krita's animation workspace brings relevant dockers forward. **Inference:** grouping by task lowers the number of simultaneously visible concepts. **Cost:** mode switches must not change document meaning or hide unsaved state, and users need a reliable way back.
5. **Separate drawing identity from exposure.** OpenToonz's Level Strip and Harmony's drawing elements distinguish a reusable drawing from when it appears. Harmony explicitly updates repeated exposures when the original changes, while independent edits require a duplicate. **Inference:** this supports retiming and reuse without silently duplicating artwork. **Cost:** the difference between blank cell, hold, linked exposure and independent copy is a significant learning burden; use labels and consequences, not colour alone. [Harmony explanation](https://docs.toonboom.com/help/harmony-22/premium/layers/about-layer-column.html).
6. **Provide equivalent routes, not identical UI.** Harmony has timeline and Xsheet views over shared scene timing, but the Xsheet omits parts of the timeline hierarchy; OpenToonz also offers both orientations. **Inference:** shared underlying data is more important than making two controls look alike. Clearly indicate view-specific operations and preserve selection when possible.
7. **Use stable anchors and explicit states.** Fixed tool palettes, selected rows, active-view outlines and layer visibility offer immediate answers to “what will my next action affect?” Harmony documents a focus border and active-view-dependent commands ([view management](https://docs.toonboom.com/help/harmony-11/sketch-standalone/Content/_CORE/_Workflow/008_Interface/002_H1_Managing_the_Views.html)). **Inference:** concise state makes dense software navigable, provided focus, selected item and disabled reason are distinguishable without colour alone.
8. **Make production colour an asset when the medium supports it.** OpenToonz linked studio palettes let style changes update linked Toonz-level artwork; palette styles have visible names/indices ([palette manual](https://opentoonz.readthedocs.io/en/latest/managing_palettes_and_styles.html)). This is not equivalent to recolouring arbitrary raster pixels. A future KomaPaint proposal must specify which artwork types can actually support links.

Dark grey surfaces, flat icons, corner radius and accent hue are **aesthetic choices**, not evidence of superior usability. Contrast, readable type, consistent focus, recoverability, and task completion can be evaluated objectively. No reviewed manual establishes a universal optimal dock width or canvas-area percentage.

## 4. Candid KomaPaint critique

### What already works in the source

- Coherent native desktop shell: menus, persistent documents and contextual panels surround a real canvas rather than imitating a marketing landing page. `MainWindow.qml` and `CanvasWorkspace.qml` bind the active document and preserve per-tab view state.
- The dock tree offers tabbing, splitting, floating, collapsing, named layouts and reset; the canvas host survives tree rebuilds. This is important infrastructure, not an invitation to replace it for stylistic reasons.
- Brush stroke previews, a modified marker and reset give presets meaningful feedback; the property panel groups live settings. The colour panel includes real HSV/hex and history rather than a fake palette.
- Visibility/lock controls on layer rows and a separate selection marker communicate consequential state; named tooltips, real keyboard shortcuts and zoom-at-pointer are useful foundations.
- Unimplemented tools are disabled instead of pretending to work; close decisions and recovery are explicitly separated. That honesty should be preserved even if the presentation changes.

### What feels unfinished or generic — evidence versus hypothesis

- **Functionality gap, not merely style:** most selection, transformation, fill, text, shape and animation capabilities are unavailable. The status of real brushes, raster layers and canvas navigation is more mature, but cannot stand in for a comic/animation production suite. A polished skin cannot fix this.
- **Disabled affordance saturation:** `ToolPalette.qml` displays many unavailable tools, and `LayersPanel.qml` includes several unavailable operations in two command bars. Hypothesis: the number of inert controls adds scanning and creates expectations of functionality. Test whether hiding or grouping unavailable future features is more comprehensible than dimming them; never hide a temporarily disabled working command without explanation.
- **Duplicated brush surfaces:** command-bar size/opacity, full Tool Property settings and a dedicated size grid coexist. They serve different input patterns, but the default hierarchy should be tested: is a 26-entry permanent size grid worth its vertical real estate for most artists? Keep expert access and the shared size steps.
- **Layer scanning is limited:** without content thumbnails or folders, names alone are less useful for a long stack; no thumbnails should be invented as decoration. Disabled vector/mask/folder controls advertise a future data model. Consider thumbnails only once backed by real content.
- **Screen-space pressure:** source specifies a roughly 84-unit-wide fixed tool rail, plus six default dock groups; colour asks for 288 content-height units and preset rows are 42 high. At the minimum 1024×640 window, these compete with canvas and scrolling. This is a layout-risk inference, not a measured screenshot or claim that content is clipped. The 18.5/63.5/18 proportions exclude the tool rail and are subject to minimum-size relayout.
- **Hierarchy and readability risk:** 9–11 pixel theme type, several subdued text tokens, and 20–24 unit controls may reduce legibility or target size, especially at scaling and in light theme. Measure actual contrast and physical sizes in both themes; do not infer compliance or failure from a token alone. The existing blue and ember states conflict with the new monochrome direction; neutral replacements must distinguish focus, selection, modification and warning without colour.
- **Context confusion:** permanent document properties compete with layers/colour even though document dimensions are infrequently changed during painting. Tool/preset, layer and document state have different scopes; a unified inspector should never conceal which object will be changed. Hypothesis: tabbing or on-demand access is more efficient for properties than a permanent default panel.
- **Animation interaction needs a different model:** a row of numbered cells and a play toggle is not an exposure editor. There is no evidence of independent drawings, editable holds, frame-linked layers, onion skin, Xsheet or actual playback in the reviewed implementation. Treat production/animation as a model and workflow problem, not a timeline restyle.
- **Project-type expectation:** `NewProjectDialog.qml` marks Comic Page, Multi-page Comic and Animation unavailable and supplies a “not available yet” tooltip; Illustration is available. This is honest in source, though its discoverability and disabled appearance still need runtime validation.
- **Navigation gaps:** source supports zoom and pan but not a verified non-destructive rotated/mirrored view or navigator overview. These are workflow gaps to validate with painters, not instructions to copy another app's navigation scheme.

## 5. KomaPaint design philosophy: one production desk, several lenses

**Proposition:** a single document/production environment whose identity comes from continuity of artwork and intent across drawing, comics and time—not a replica of any one palette layout. The earlier suggestion to retain “ink and ember” as a visual language is superseded by the strict neutral direction in §§12–13; the product identity should come from reliable interactions, clear scope and transitions between tasks.

### Borrow, adapt, reject

| Principle | Action | Reason / condition |
|---|---|---|
| Canvas plus stable tool and state anchors | **Borrow** | Frequent operations should remain predictable, but anchors can collapse and must be keyboard-accessible. |
| Contextual properties and deep editing | **Adapt** | One named inspector with tool/document/layer scope and an explicit advanced path; avoid silently changing scope. |
| Workspaces/rooms | **Adapt** | Task lenses change visible panels, not the underlying project, shortcuts or document identity. Save custom layouts and provide a reversible reset. Do not present unfinished modes as available. |
| Local quick access | **Adapt after testing** | User-configurable favorites near canvas may reduce pen travel; do not copy Krita's circular arrangement or conflict with context menus/stylus input. |
| Timeline and Xsheet | **Adapt concept, not appearance** | Different projections of a shared time/exposure model; honor view-specific functions. Show linked vs duplicated drawings explicitly. Requires real model and undo semantics first. |
| Production palettes and assets | **Adapt** | Reusable named colours/reference material with explicit provenance; linked recolouring only where supported by the actual artwork model. |
| Always-visible full control catalog | **Reject** | Density is justified by task frequency, not sheer number of options. Maintain menu/search/shortcut access and explain unavailable commands. |
| Cosmetic imitation and dark-theme-as-quality | **Reject** | A consistent identity is not a copied arrangement, icon set, colour scheme or default theme. Validate accessibility and task performance in both themes. |

**Beginners and experts:** start with one intelligible painting setup, names and a small number of meaningful defaults; expose advanced settings, shortcuts, custom layouts and high-density views without moving fundamental commands or replacing the novice workflow. Focus, selection, dirty state and destructive consequences should have text/shape cues in addition to colour.

## 6. Proposed workspace structure (concept only)

```text
Application menu + compact command/state strip
Document / project context and tabs
┌──────────┬─────────────────────────────────────────┬──────────────────────┐
│ stable   │ Shared artwork / scene view             │ Context: active      │
│ tool     │ (pan, zoom, fit; future rotation etc.)  │ tool, layer, colour  │
│ access   │                                         │ and assets as needed │
├──────────┴─────────────────────────────────────────┴──────────────────────┤
│ Optional task surface: page organiser OR timeline OR exposure sheet      │
└───────────────────────────────────────────────────────────────────────────┘
Status: active document, scope, view, save/recovery state as relevant
```

This is a relationship diagram, **not a proposed pixel layout**. Panels can dock/tab/float, be collapsed or restored; a canvas-focus command should be reversible. Retain a discoverable menu route for every hidden panel. Size defaults only after measuring 1024×640, 1366×768, 1920×1080 and high-DPI real screens.

- **Illustrate / Paint:** canvas, tool/preset choice, essential brush properties, colour and layers. Advanced brush editor and document properties on demand. Distinguish selection/focus from painting state.
- **Comic:** same painting tools and layer semantics plus a page navigator, page order, templates and lettering/frame tools **when actually implemented**. Page context should be visible; switching pages must not silently discard edits.
- **Animate:** same drawing surface and colour/brush system plus a resizable timeline for frames, exposure and layer context, transport and onion-skin controls when supported. Drawing identity, held exposure, blank and copied drawing need distinct labels and undoable operations.
- **Production / timing:** a dedicated optional exposure-sheet surface, drawing inventory, shot/scene context and palette/asset references. Horizontal and vertical views must operate on the same data where their scope overlaps; clearly label any differing scope. These are future concepts, not present features.
- **Cross-lens invariants:** same current document, save state, selected artwork, colour, brush semantics and navigation shortcuts unless a change is explicit. Do not equate the still-image layer stack with a future scene hierarchy without a model that can represent both.

### 10.3 Cross-application architectural conclusions

1. **One authoritative state, several deliberate views.** Krita's brush chooser and paint-op box observe the current canvas preset; OpenToonz views access shared tool/palette/Xsheet handles. For KomaPaint, `Workspace.brush` is already shared by multiple QML controls. Preserve that state contract; multiple controls are justified when they serve different tasks. The question is visibility and semantics, not eliminating all repeated access.
2. **Panel hosts and panel content have separate responsibilities.** Factories and named panels make layouts possible while each panel remains specialized. KomaPaint already separates `DockModel`/`DockWorkspace` from panel components. No code replacement is proposed.
3. **Context is explicit and observable.** Krita scopes tool options to a canvas controller; OpenToonz updates on tool, level, frame and column signals. For KomaPaint, label whether a value affects a brush preset, selected layer, active document, view or future scene. Rebinding when document/context changes must remain correct. Do not introduce new infrastructure merely to imitate a class structure.
4. **The action may be reused even when the widget is not.** OpenToonz surfaces shared command actions in menus and bars. KomaPaint has duplicate handlers for zoom in toolbar/status/menu; they already call the same `Workspace` operations. Investigate consistent labels, enablement and shortcuts before proposing a command framework.
5. **Restorable customization is part of usability.** Both open-source examples store layout structure and preferences. KomaPaint already offers named layouts and reset; retain their behavior. Neither source proves a saved layout is necessarily usable at every size.
6. **Maintainability is not uniformity.** OpenToonz's tool-properties implementation contains both general property groups and tool-specific code; Krita uses an extensible widget host but also specialized dockers. A shared foundation should not force the timeline, colour picker and layer list into an identical visual container.

## 12. Restrained, human-directed creative interface: analysis

“Mature,” “quiet,” “generic,” and “AI-generated” are subjective descriptions, not diagnoses. The user has chosen a neutral visual direction. The following are testable principles for applying it without mistaking taste for evidence:

| Decision | Rationale and useful constraint | How to test, not assume |
|---|---|---|
| **Intentional empty space** | Leave breathing room around groups and artwork, not a large moat around every control. Empty list space can communicate capacity; unnecessary padding can push layers, brush names or timeline rows out of view. | Compare visible rows, target acquisition and error rate at 1024×640, 1366×768 and larger; allow users to collapse panels. |
| **Group by task and scope** | Align label/value pairs and group controls that affect the same object. Frequent brush, layer and colour decisions deserve shorter paths than rarely changed document settings. | Ask users what each control edits and measure time to change a brush, then a document setting. Do not assume a universal use frequency. |
| **Borders are functional** | One divider can establish a dock edge; a field outline can identify an editable region; a focus outline can locate keyboard focus. Repeating outlines around every section can create false hierarchy and visual noise. | Remove a candidate divider only in a prototype; verify users can still identify boundaries, controls and focus. Hairlines for decoration need not carry interaction state. |
| **Typography communicates role** | Use a small number of sizes and weights, sentence-case labels and predictable alignment. Monospace/tabular figures are useful for changing numerical readouts, not mandatory for all labels. Long names need truncation with accessible full text. | Test long/localized strings, scale, visual acuity, contrast and legibility. Smaller is not inherently professional. |
| **State is not a coloured accent** | Active, selected, hovered, pressed, disabled and keyboard focus are different facts and can coexist. Use a combination of neutral surface, outline, weight and shape; e.g. selected row plus distinct focus outline. | Test grayscale, high DPI, keyboard-only, colour-vision differences and selected+focused/hovered combinations. Do not rely on brightness alone if adjacent artwork has similar luminance. |
| **Icons plus text when identification matters** | Familiar compact actions benefit from icons; presets, tool types, layer names and infrequent destructive commands benefit from labels. A tooltip is supplementary, not the only accessible name. | Test first-use identification and after learning; check symbolic icons at actual scaled sizes, not only in a design sheet. |
| **Canvas dominance is functional** | Surrounding chrome should not draw attention away from artwork, but artists must see active tool, colour and editable layer. A collapsed canvas-only setup is not automatically better for complex timing work. | Measure unobstructed usable canvas and time to reaccess hidden controls by task; evaluate painting, layer editing and animation independently. |
| **Consistent grammar, specialized surfaces** | Use shared text, spacing, focus and action conventions; allow a layer list, colour plane and frame grid to have distinct structures. | Ask whether state and scope are predictable across panels without making each panel look identical. |

**Screenshots are evidence of arrangements, not proof of outcomes.** CSP's docking example, OpenToonz's pane composition and Harmony's labeled timing controls in §1.1 suggest these hypotheses. They do not prove reduced fatigue, faster work or a particular optimum. The W3C [contrast](https://www.w3.org/TR/WCAG22/#contrast-minimum), [non-text contrast](https://www.w3.org/TR/WCAG22/#non-text-contrast) and [focus appearance](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html) guidelines are useful design benchmarks for this desktop UI, not a claim that the current application meets WCAG or that web CSS pixels automatically equal Qt logical pixels.

## 13. Proposed KomaPaint monochrome design system — specification for research, not implementation

### 13.1 Identity and colour boundaries

**Direction:** a neutral production desk with the artwork, content and operational state foregrounded. No chromatic highlight, decorative colour block, glow, colourful border or aesthetic gradient in application chrome. The identity is the consistent relationship among canvas, scope, typography and controls—not a copied palette arrangement or a brand accent.

**Functional colour is not decoration:** actual artwork, brush stroke samples where relevant, foreground/background swatches, colour selector hue/HSV gradients, material previews, and meaningful existing file/content colours must remain accurately coloured. Neutral chrome must never desaturate or distort artwork or colour-selection data. Warning/error messages use a neutral icon/shape, concise text and explicit consequence by default; any future exception for safety-critical semantic colour requires separate justification and must not rely on colour alone.

### 13.2 Candidate neutral palette

The following opaque sRGB values are **candidate research tokens**, not a theme file or a final accessibility certification. All hex values are neutral (`R=G=B`). Contrast values assume full-opacity text on the exact adjacent surface, not antialiasing or any overlay.

| Role | Dark candidate | Light candidate | Use |
|---|---|---|---|
| Outer chrome | `#2C2C2C` | `#EEEEEE` | Menus, shell, inactive strip. |
| Panel / working surface | `#383838` | `#F4F4F4` | Dock bodies and dialogs; avoid individual cards. |
| Input / recessed well | `#292929` | `#FFFFFF` | Editable fields or a functional preview well, not every group. |
| Canvas surround | `#454545` | `#E8E8E8` | Neutral surround, not artwork; allow viewing conditions to be evaluated. |
| Hover | `#444444` | `#E4E4E4` | Temporary pointer indication; not the selection indicator. |

Spot checks using the WCAG relative-luminance formula: dark primary on panel **10.02:1**, dark secondary on selected **4.72:1**, dark primary on selected **6.89:1**, light primary on panel **14.47:1**, light secondary on selected **5.08:1**. Focus candidate against dark panel **7.01:1** and light panel **8.86:1**; against selected surfaces approximately **4.82:1** and **6.64:1** respectively. These are pair calculations, not a rendered-interface audit; check hover/pressed, selected+focus, translucent overlays, actual fonts, adjacent surfaces and focus *state-change* contrast individually. Separator contrast is intentionally not asserted to satisfy a functional boundary. Disabled appearance is not the only way to explain availability.

### 13.3 State grammar and component rules

| State | Proposed neutral encoding | Scope / accessibility check |
|---|---|---|
| Idle | Legible text or icon against the host surface; do not draw a box around every button. | Identify enabled controls without requiring hover. |
| Hover | Subtle temporary neutral surface change, no movement or glow. | Distinguishable from a checked selection. |
| Selected / active | Neutral selected surface plus a consistent edge, check, shape or font-weight cue appropriate to the component. | Current document, tool, layer and frame are separately scoped; selection is not keyboard focus. |
| Keyboard focus | High-contrast 2-unit outline, independent of selection. | Must remain visible on selected, pressed, light/dark, artwork-adjacent and custom backgrounds; no reliance on hover. |
| Pressed | Brief neutral tonal change; retain checked marker. | Not mistaken for persistent active state. |
| Disabled / unavailable | Neutral muted treatment, explanatory accessible name/tooltip and visible text where essential. | Distinguish not-implemented from temporarily invalid; no colour-only state. |
| Warning / error | Text with a recognizable warning/error shape, affected object and corrective action. | Semantic message must remain understandable in monochrome, by screen reader and without the icon. |
| Unsaved | Neutral dot or explicit marker **plus** accessible “unsaved changes” label/tooltip. | Do not conflate dirty state with selected tab or current tool. |

A low-contrast separator is acceptable only when it is decorative or redundant; essential focus, selection and boundaries require sufficient differentiation. The W3C web guidance gives **4.5:1 for ordinary text** and **3:1 for required non-text indicators** as useful minimum targets, with exceptions; focus appearance's area and state-change test is AAA. Use the guidelines as benchmarks, not a certification claim for this Qt desktop app.

### 13.4 Typography, spacing, borders and iconography

- **Typography:** one platform-capable UI sans family and sensible fallback; candidate body/field label **12–13 Qt logical pixels**, panel title **13–14** medium, secondary metadata **11–12**, dialog heading **15–16**. Values are starting hypotheses, not physical-size guarantees. Avoid 9 px tracked all-caps as the default for important labels. Support platform text scaling and localization; verify legibility on real hardware. Use tabular digits for zoom, frames and numeric values where available.
- **Spacing:** derive from a small 4-unit rhythm, with 4–8 between related controls, 8–12 between groups and 12–16 around dialogs where space permits. The existing 2-unit micro gaps may be appropriate inside dense grids; do not impose a single padding value on every surface. Allow enough scrollable space instead of clipping or squeezing labels.
- **Targets:** candidate minimum **24×24 logical units** for routine pointer controls with generous spacing; prefer **28–32** or larger for frequent pen targets. A visible 1-unit line may have a larger invisible hit area. Qt units are not WCAG CSS pixels and exceptions/context matter; test actual physical size at Windows scaling, with pen and mouse. Avoid shrinking controls merely to reach a density target.
- **Borders and surfaces:** one shared dock edge or alignment where it provides structure; 1-unit border for fields and popup boundaries where needed; 2-unit focus cue. No stacked card/section/input borders by default. Radius **0–3** is a candidate for controls; avoid visually prominent rounded containers, decorative shadows and unnecessary separator lines. The canvas boundary remains functional against light/dark artwork.
- **Iconography:** retain existing authored tool/layer asset shapes where they communicate well; use neutral tints, consistent optical size and visual weight. Audit mixed PNG icons and `KpGlyph` vector strokes at small and high-DPI sizes. Provide text or accessible names/tooltips and test selected/disabled/focus shapes. Do not recolour meaningful colour samples into grayscale.
- **Motion:** no ornamental motion or glow. Any existing transition should be short, purposeful and respect reduced-motion preferences where available; source alone does not establish current reduced-motion behavior.

### 14.1 Ranked **visual research** recommendations

The list below supersedes §7 for this interface-only continuation. It is not authorization to implement.

1. **P1 — Establish neutral state semantics and contrast:** prototype light/dark neutral token candidates; verify text, focus, selected, hovered, disabled, unsaved and error states, including state combinations and meaningful colour exceptions. Preserve the two-theme architecture. Acceptance evidence: contrast pair matrix and keyboard/pen tests, not colour preference alone.
2. **P1 — Audit vertical and horizontal space in the actual running UI:** capture 1024×640, 1366×768 and 1920×1080 at relevant scaling; record canvas rectangle, visible layer/preset rows, scrolling and clipping. Compare task completion with and without redundant decoration before changing dimensions.
3. **P1 — Simplify nested surfaces and over-emphasis where evidence supports it:** start with New Project's project tiles and nested preview cards, then preview wells and repeated rules. Confirm groups, focus and editability remain clear.
4. **P1 — Make typography and icons readable:** compare 12–13-unit body candidates against existing 9–11-unit tokens at real DPI; evaluate mixed icon weight, truncation, localization, tooltips and accessibility. Keep density configurable rather than globally enlarged or compressed.
5. **P2 — Rationalize repeated access by task, not by count:** observe brush size/opacity and zoom use across toolbar, properties, size panel and status. Keep duplicates that reduce travel or provide feedback; consider default visibility only after testing.
6. **P2 — Reduce unavailable-control noise without concealing capability state:** compare current dimmed tool/command clusters against grouped or progressive presentation. Distinguish future features from temporarily inapplicable commands and retain discoverability.
7. **P2 — Tune contextual panels and canvas hierarchy:** validate active tool, selected layer, active document and focus scope; test collapsing/tabbing infrequently used document properties. Retain freedom to customize and restore.
8. **P3 — Explore future animation/comic visual surfaces only after their functional models exist:** use truthful existing controls and real frame/production semantics; avoid inventing timeline polish that misrepresents capability.

### 14.2 Untouched behavior and components

During this phase **all application source and UI components remain untouched**. In a later visual phase, preserve by default unless evidence and regression testing support a specific change:

- `DockModel`/`DockWorkspace`: docking, panel IDs, canvas lifetime, drop indication, layout save/reset and user layouts.
