# Painting resource and undo architecture audit

Audit of branch `arena/85d1cfaa-komapaint`, code at `575a0ebc4cced196fe1b6455bd88a7db4e78dae2` (the subsequent commit adds only the measurement test). This is an investigation and proposal, not a change to painting behavior. MiB = 1,048,576 bytes.

## Executive finding: observed message is ambiguous

The reported message originates in `CanvasViewport::beginStroke`, `continueStroke`, and `endStroke` (`src/app/CanvasViewport.cpp:242–245,263–265,278–283`). `BrushStroke::stamp` (`src/drawing/BrushEngine.cpp`) converts several different `SparseTileStore::WriteResult` values to a boolean and discards the reason. A rejected history callback is also returned as `HistoryLimit` for both a budget rejection and a caught allocation exception (`src/history/UndoStack.cpp:29–41`; `src/canvas/SparseTileStore.cpp:71–74`). Invalid input can also result in the same generic viewport warning. **The exact cause in the user's session cannot be determined retrospectively from that message**; no session counters, failure code, canvas, layer or stroke data were captured. Calling it the 256 MiB layer limit would be speculation.

However, a real and very restrictive **64 MiB history budget** is a compelling, independently reproduced cause. It is global to the active workspace history, not per layer, and stops new changes when full. It is not configurable through the current UI. See the reproducible measurement below. This is a demonstrated failure mode, not proof of the particular user's failure.

## Measurement: actual brush, tile store and UndoStack

Added `tests/unit/TestHistoryAudit.cpp`, run using MSVC/Qt 6.8.3 on the Windows Actions runner, [run 42859245667](https://github.com/katsuhirojiro/KomaPaint/actions/runs/42859245667). A 3000 × 2000 layer received 4-pixel alternating-color brush strokes at one point, each changing one existing tile. The first stroke created that tile. Using the real `BrushStroke` and `UndoStack`:

* One 256 × 256 × 4-byte ARGB tile = **262,144 bytes** of layer pixel payload, even if one pixel or an edge fragment is used.
* Every stroke touching one tile is **charged 524,800 bytes** (two full tiles + 512 bytes); the first stroke's absent-before state actually has no before pixel buffer, so its retained pixel payload is one tile, not two. Subsequent strokes retain two complete 262,144-byte pixel arrays per touched tile, even when just a few pixels changed.
* **127** strokes were accepted. Reported history charge: **66,649,600 bytes**; allocated layer pixel payload: **262,144 bytes**. The 128th stroke failed; a direct store write during that attempted stroke returned `HistoryLimit`. All **127 undos and 127 redos** completed, including reclamation and recreation of the tile. The runner reported 34 ms for the entire small synthetic test; this is not a real-device latency benchmark.
* The limit is 67,108,864 bytes; 127 charges leave 459,264 bytes, less than the next 524,800-byte reservation. A stroke touching two tiles costs 1,049,600 bytes and the same budget fits 63 complete such charges (calculation, not a measured workload). A four-tile stroke costs 2,099,200 bytes.

`memoryBytes` is **accounted reservation**, not process RSS, exact allocation size, or a measurement of Qt/GPU memory. Actual vector capacity, allocator bookkeeping, command metadata, dirty maps, temporary copies, and other allocations are not comprehensively measured. `finishCapture` removes unchanged tile entries but does not subtract their charge when a partially changed stroke is committed; `vector::clear` also does not necessarily free its capacity. A whole unchanged stroke is discarded with zero charge. These details can make reported charge differ from actual retained payload in either direction. The test above is deterministic evidence of the limit, not a representative long-session memory profile or proof of Windows tablet behavior.

## End-to-end lifecycle and integrity

1. `ui/components/CanvasWorkspace.qml:46–76`: mouse and pen `PointHandler`s call `CanvasViewport::beginStroke`, `continueStroke`, and deferred `endStroke`; cancellation calls `cancelStroke`. Pressure is forwarded for pen; mouse uses 1.
2. `CanvasViewport::beginStroke` (`src/app/CanvasViewport.cpp:192–247`) validates the active visible/unlocked layer, starts `UndoStack::beginStroke`, copies brush settings, creates a `BrushStroke` and maps viewport coordinates to document pixels. Move/end continue the same stroke. Layer changes/cancellation call `UndoStack::cancelStroke`.
3. `BrushStroke::extend` interpolates dabs; `BrushRasterizer::dab` calculates coverage and premultiplied source-over color for each pixel, then `SparseTileStore::setPixel`. Notifications are coalesced per dab. Per-pixel rasterization/lookup and debug logging in `CanvasViewport` are potential responsiveness costs; no real-device performance profile has yet been captured.
4. `SparseTileStore::setPixel` (`src/canvas/SparseTileStore.cpp:48–94`) checks bounds, premultiplied channels and per-layer budget; it allocates a zero-filled tile for the first nonzero pixel. Before mutation, the history callback records the original state once per tile and preallocates an after buffer. A failed callback prevents that pixel change, and erases a newly allocated tile. Dirty tracking is marked before the pixel changes. A tile is reclaimed once its nonzero count becomes zero.
5. `UndoStack::commitStroke` copies final tile states, discards fully unchanged entries, removes redo commands after the cursor, and appends the stroke. The representation is **whole-tile before/after snapshots**, not a compact pixel delta or full-document snapshot. Consecutive strokes duplicate identical tile states: a stroke's after generally duplicates the next stroke's before, and unchanged pixels are copied into both states. A no-op stroke is discarded. Redo entries remain charged until a new stroke *commits*, so a full history can prevent a new stroke even after undo; the future redo entries cannot be discarded until that commit occurs.
6. On a mid-stroke failure, the viewport commits earlier changes as one partial undoable command and reports the generic warning. `cancelStroke` attempts atomic restoration; if that fails it commits the partial stroke rather than silently losing undo. `restoreTiles` stages replacements and dirty changes before mutation, preserving artwork/cursor on failure; it can itself fail for memory, tracking, or layer-budget reasons (`SparseTileStore.cpp:95–148`, `UndoStack.cpp:82–116`). Exact 32-bit premultiplied values, including alpha and missing-tile state, are stored. A failure to begin before any change creates no command.
7. Document replacement clears session history; history is not saved into `.koma`. Layer deletion is not undoable and clears history with a warning (`WorkspaceState::connectLayerDeletion`); a new committed stroke normally discards the redo branch. These are important limits on the objective of undoing every operation throughout a session.

## Other resource consumers and limits

* `SparseTileStore::DefaultPixelBudget` (`src/canvas/SparseTileStore.h:18`) is **256 MiB per layer**, equal to **1,024** full-size allocated tiles. A completely filled 8192 × 8192 layer uses exactly that pixel payload. A 10,000 × 10,000 layer requires 40 × 40 tiles, or **400 MiB** of pixel payload, including partially filled edge tiles, so the current per-layer ceiling prevents completely painting it. Conversely, touching one pixel in each of 1,024 widely separated tiles consumes the same budget. A full 3000 × 2000 layer requires 12 × 8 = 96 tiles, **24 MiB** pixel payload. The fixed ceiling is restrictive for larger work, while multiple layers can multiply memory without any global budget. Raising it alone increases risk and does not solve the 64 MiB history bottleneck.
* Layer pixel accounting excludes hash-table and allocator overhead. `DirtyTileTracker` permits up to **65,536 pending dirty tiles**, tracks versions and may allocate; tracking exhaustion or allocation failure also produces the generic warning. Typical layer limits make that count less likely for a single fully occupied layer, but dirty entries can outlive tile reclamation until acknowledged.
* Undo reserves an after tile before modification and retains a before tile if present. Applying undo/redo stages tile copies and dirty-map copies, and briefly holds current and replacement tiles together; these peaks are outside the reported history budget. A memory-starved undo may safely fail without moving the cursor; an accepted stroke is not guaranteed to undo successfully under all future resource conditions until resources recover.
* `CanvasViewport` has an independent **32 MiB** composite-image cache (`CanvasViewport.h`, `composedTile`), a 4-byte-per-pixel viewport frame with a 32-million-pixel cap (up to 128 MiB frame payload), plus temporary composite tile vectors and QImages (`CanvasViewport.cpp:172–190,297–394`). The actual viewport frame depends on viewport size, not canvas size. Cached images can be evicted; they do not directly charge the history limit but compete for process memory. GPU/Qt allocations and device pixel ratio effects need profiling. The brush object itself is small; the large in-progress buffers are in history.
* Saving builds a whole illustration payload in memory; opening stages tile buffers and `restoreTiles` makes additional copies (`src/files/DocumentFile.cpp:340–408,435–482`). Large artwork may therefore encounter peak memory during save/open despite otherwise working. This audit does not change serialization.

## Reference products: observable behavior, not inferred internals

* Krita documents a configurable undo-command count (0 means unlimited) and a memory threshold for swapping undo data to disk, with a finite swap-file limit and location. It warns that exhausting both memory and swap can freeze the app. Its FAQ describes an on-screen resource indicator. See [Krita General Settings](https://docs.krita.org/en/reference_manual/preferences/general_settings.html), [Performance Settings](https://docs.krita.org/en/reference_manual/preferences/performance_settings.html), and [FAQ](https://docs.krita.org/en/KritaFAQ.html). These are user-facing descriptions, not evidence of its exact data structure.
* Clip Studio Paint documents configurable undo levels, memory allocation, virtual-memory path and memory-use warnings, and warns that more undo levels can slow down or terminate the application. See [Clip Studio Paint Preferences](https://help.clip-studio.com/en-us/manual_en/720_preferences/Preferences.htm) and [official performance guidance](https://support.clip-studio.com/en-us/faq/articles/20210101). Its private undo representation is not established by those documents.
* Neither reference proves unlimited undo with finite resources. Finite RAM and disk, plus arbitrary user activity, make an unconditional promise to retain every stroke impossible. A product must explicitly communicate and negotiate resource exhaustion.

## Proposed incremental architecture (not implemented)

1. **Diagnose first.** Preserve structured failure causes from history reservation, allocation, tile budget, dirty tracking and invalid input through brush and viewport. Include resource category, current/limit counters and whether a partial stroke was committed. Avoid exposing a false exact cause when allocations fail within the history callback. Surface a clear, non-repeating warning with safe options and early pressure indicators. Existing saved artwork must not be touched. Obtain an anonymized reproduction: canvas dimensions, layers, brush settings, stroke count, affected tiles and memory counters. This is necessary to identify the original incident.
2. **Compact exact history.** Record each changed pixel's original and final 32-bit premultiplied value once per stroke using tile-local spans/runs or blocks, including an explicit absent/present tile state. Deduplicate repeated writes within the same stroke. Choose measured adaptive encoding per tile (sparse spans/XOR plus optional lossless compression vs full snapshots for dense changes), and do not retain unchanged records. Avoid recording just input events: future brush algorithms and pressure rounding can make replay nondeterministic. Preserve ordering, layer identity and alpha bit-for-bit. Use bounded temporary structures, not an unbounded per-pixel map.
3. **Transactional resource policy.** Account for artwork, history, redo, in-flight strokes, cache, undo/redo staging and file I/O separately under an overall adaptive memory budget with headroom. Reserve the storage needed to preserve a change *before* applying it; make accounting match actual capacity where practical. Treat replacing a redo branch transactionally: never drop it for a no-op or failed stroke. When resources cannot be secured, leave artwork and all accepted history unchanged, or preserve an explicitly reported undoable partial stroke using a tested, allocation-safe path. Do not silently prune history. Enable cache eviction under pressure before refusing edits.
4. **Bounded spill, not unlimited memory.** Once compacted history exceeds a configurable RAM threshold, move older immutable records to a bounded session-local disk store in the background. Use checksummed records, atomic publication and bounded write/read queues; keep a record in RAM until its disk write is verified. Account disk reservations, free-space safety margin, quota, concurrent I/O and cancellation; protect private artwork via an appropriately restricted temp location and cleanup. Disk full, permissions, corruption, removal and read errors must keep the cursor/artwork intact and produce actionable diagnostics. Undo can be slower while loading a cold record; prefetch with limits. Confirm user expectations around recovery vs session-only data; do not advertise a swap file as crash recovery. At both limits, ask the user to save, expand/change storage, or explicitly confirm discarding history; never silently evict history.
5. **Layer limits and UX.** Replace the isolated fixed per-layer ceiling only once the document-wide manager and save/open temporary peaks are understood and enforced. Configure bounded RAM and disk budgets with sensible device-aware defaults and system headroom; offer usage and storage location in Preferences. Explicit user-approved history clearing is already available and must remain clear about irreversibility. No arbitrary setting can guarantee an infinite session on finite storage.
6. **Performance.** Batch raster/dirty updates and replace linear scans of all touched tiles with bounded efficient lookup; profile allocations and p50/p95/p99 input-to-render latency on lower-end Windows, including slow disk and zoomed-out multi-tile strokes. Compression/spill must not block pointer handling; do not change the brush's pixel output without exact comparison.

## Verification plan before any rollout

* Seeded short/single-pixel and long strokes: hundreds/thousands, same tile and many tiles, large canvases and multiple layers. Record true process working set/private bytes, peak and retained bytes by category, time per stroke and undo, and disk I/O. Compare exact before/after every operation and all alpha bytes, not merely a sampled pixel; include screenshots and Windows tablet input.
* Undo/redo all accepted strokes repeatedly, redo-branch replacement, empty strokes and fill-to-limit behavior. Exercise absent→present, present→absent, edge tiles, erasing/reclamation, layer isolation, layer deletion and document replacement. Verify cursor and pixels remain unchanged on failure.
* Inject failures at every allocation, reservation, flush, read, checksum and restore stage; include full/unavailable/slow disk and interruption. Confirm partial accepted paint is always recoverable by undo, or is rolled back atomically; never silently drop history.
* Save and reopen after long painting and undo sequences, compare all tile pixels/metadata and verify session-only history behavior. Exercise peak memory during file operations and recovery from failed saves. Retain the existing New Project, Save/Open and QML painting tests.
* Only the 127-stroke synthetic reproduction and existing suite have been run for this audit. Thousands of strokes, disk spill, Windows physical tablet and process-memory profiling are **proposed tests**, not completed results.
