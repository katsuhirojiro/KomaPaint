# Technical design: adaptive undo and shared resource management

**Status: proposal for product-owner approval. No painting or file-format implementation has been changed.** This follows [the resource audit](painting-resource-audit.md); the actual cause of the reported user incident remains unknown because the existing warning discards the failure reason. The reproduced 64 MiB history failure is a demonstrated bottleneck, not proof of that incident.

## Product contract and scope

* No fixed, hard-coded undo-step count. Keep the entire **retained editing branch** for the active document session while resources permit. History is lossless, ordered and layer-isolated. RAM and bounded disk capacity work together; the session length is limited by actual resources and user policy, not a fixed stroke count.
* Never silently prune history to make space. Before a committed edit would discard a redo branch, obtain explicit confirmation or offer to cancel; a no-op, rejected stroke or failed transaction must not discard it. New/Open, closing a document, clearing history and deleting a layer must likewise disclose history loss unless history is retained or those operations are made undoable. Existing layer deletion currently clears history; a production rollout must address it rather than claim every editing operation is retained.
* **Accepted** means the whole stroke has been successfully committed to both the artwork and the recoverable session history. Every accepted stroke must restore exact premultiplied 32-bit pixels and tile existence in reverse and forward order. Every subsequent operation that changes those pixels must participate in the same command ordering; unsupported untracked mutations must be prevented or explicitly end the history with consent.
* Painting is transactional at stroke level. Failure or cancellation before commit rolls the whole stroke back; no partial or unrecorded paint is accepted. An in-progress stroke may be displayed tentatively, but is not committed and can disappear on failure. The UI must make that state and failure clear.
* This is an integrity guarantee under the documented storage contract: if a backing file becomes unavailable or corrupt, the application must not apply a partial undo or move its cursor. It cannot physically guarantee successful replay after unrecoverable disk loss, external data corruption, process termination or operating-system failure. Instead it retains all still-readable data, reports the problem and offers retry/change storage/recovery. Session history is not a crash-recovery system or part of `.koma` in this proposal.

## Binding acceptance criteria added by the product owner

These criteria govern the eventual implementation and release; they are **not yet verified** by the encoding experiment below.

### Exact restoration

* For every accepted command, undo must restore the exact state immediately before it and redo the exact state immediately after it: all 32-bit premultiplied pixels including alpha; tile absence/presence, coordinates and edge geometry; and the affected layer's stable identity and applicable state. Compare complete state, not sampled pixels or visual similarity. Layer state includes layer ordering, visibility, lock, opacity, name, active selection and document modified state **where the command is responsible for changing them**. A brush stroke must not unexpectedly roll back a later unrelated layer-property change; chronological layer operations must be history commands themselves or, until supported, be blocked or explicitly disclose history loss. The saved/modified indicator needs an explicit save-point model, not an assumption that undo always makes the document unmodified.
* Replay uses stored pixel values, not re-rendered input, lossy compression or color conversion. Undo/redo must restore tile creation and reclamation exactly and preserve untouched layers. Disk read errors and checksum failures leave artwork, layer state and history cursor unchanged; retry is possible. No design can promise replay after unrecoverable destruction of the only stored history copy.

### Atomic failure semantics

* A stroke is accepted only at the joint publication of complete artwork and its recoverable history record. If required history admission, tile/metadata allocation, publication or replay-reserve preparation fails before acceptance, the **entire stroke** rolls back to its pre-stroke pixels, tile allocation, layer state, modified/save-point state, history cursor and redo branch. This includes failure after many visible tentative dabs. Pending repaint invalidations may differ internally, but must lead back to the correct pre-stroke display. No partially committed stroke and no silently unrecorded paint are allowed.
* Rollback must not allocate: hold the actual original tile ownership/nodes, reserved notification capacity and metadata from before each mutation. Reserving a numeric budget alone is insufficient. Exercise every failure point, including the last tile and command-publication boundary. Serialization, disk I/O and optional compression are outside the no-fail publication critical section.
* If optional compression fails but a complete admitted lossless fallback exists, keep that fallback; this is **not** a history-storage failure and the stroke can be accepted. If a later attempt to spill already accepted history fails, retain its valid RAM copy and leave current artwork and cursor unchanged; pause further admissions if safe capacity cannot be maintained. A later spill failure must not retroactively erase an earlier committed stroke. The user receives the precise cause and actionable choices.

### Actual memory measurement: mandatory before rollout

* Measure **actual allocated capacities**, not merely logical payload or an assumed per-record header. Attribute live and peak bytes to tile backing stores, layer/document metadata, history command/index metadata and allocator overhead, temporary before/after versions, rollback and replay reserves, compression and decompression workspaces and output, queues and pinned records, compositor caches, viewport frames, save/open staging and spill buffers. Count shared allocations only once and separately report reservations versus committed allocations.
* On Windows collect process private committed bytes and working set, including peak values, using OS-level process counters, with time-series samples and operation-boundary snapshots. Collect managed allocator/capacity telemetry and use a native allocation profiler or ETW for attribution and short-lived peaks; sampled RSS alone can miss transient allocations. Measure GPU/Qt memory where tooling permits and label unmeasured areas. Do not add process totals to category allocations as though they were independent; explain differences, fragmentation and OS page rounding. Report warm baseline, retained increase per stroke, peak while drawing/committing, peak during cold and hot undo/redo, save/open and simultaneous compression/spill.
* Compare existing snapshots, delta-only, compressed snapshots and hybrid using the **same actual application workloads**, not just the offline encoded payload calculation. Run blank, sparse, realistic layered artwork, alpha-heavy and incompressible inputs on lower-end and representative Windows PCs. Publish distributions across small, medium, large and multi-tile strokes and thousands of strokes. The measurements in the next section are only a preliminary encoding comparison and do not satisfy this release gate.

### Responsiveness: mandatory before rollout

* No full-tile compression, decompression or disk read is performed synchronously on the pointer-input/UI path. Accept a preallocated exact fallback first; perform optional compression and bounded spill on workers, retaining the fallback until verification and atomic publication. Bound queue size, memory and CPU concurrency; do not allow background work to starve the UI. Hot undo/redo must not require disk or mandatory decompression; reserve a configurable, budgeted hot working set. Cold undo uses asynchronous reads with a visible busy/progress state, cancellation where safe, and a bounded queue; do not claim cold history is instantaneous on slow media.
* Establish the current version's latency baseline on an agreed lower-end Windows PC with 60 Hz or better display, real mouse and tablet, realistic artwork, and both warm and cold history. Record p50/p95/p99 input-to-visible-update latency, frame misses, longest UI-thread task, pen-up-to-commit latency, hot and cold undo request-to-visible-restoration, background CPU contention and disk stalls. Compare identical seeded workloads and repeat runs; include active compression, low RAM and slow/full disk. Define the numerical release thresholds with the product owner after collecting that baseline, and require manual artist assessment of whether delay is noticeable. A passing percentile alone is not sufficient when individual stalls are obvious.
* If compression causes noticeable interactive delay or misses the agreed threshold, throttle/defer it or fall back to the uncompressed representation; do not claim compliance merely because compression ran on another thread. At resource saturation show a clear non-blocking status and safely reject/roll back the current stroke if it cannot be admitted. Finite RAM and slow or failed storage prevent an unconditional guarantee of imperceptible cold undo in every environment.

## Measured encoding comparison

`tools/history-design/measure.py` builds the **existing** CPU brush and sparse tile store with g++ and records the actual before/after tiles for deterministic synthetic strokes on a 3000 × 2000 canvas. Local run: Linux x86-64, GCC 12.2, Python 3.11.2, zlib 1.2.13. Raw results: [sample-results.csv](../../tools/history-design/sample-results.csv). Reproduce with `python3 tools/history-design/measure.py` on a little-endian system with g++ and Python zlib. No Qt, GUI, allocator or disk-backed implementation is involved.

* **Small:** 4-pixel brush, stationary dab, 16 changed pixels, 1 tile.
* **Medium:** 16-pixel brush, 450-pixel line, 7,416 changed pixels, 3 tiles.
* **Large:** 96-pixel brush, 1,200-pixel line, 122,568 changed pixels, 6 tiles.
* Backgrounds are absent tiles, uniform partially transparent pixels, and seeded opaque random pixels. The experiment verifies byte-exact forward/reverse delta reconstruction and compressed snapshot decompression, including alpha.

All values below are **bytes of measured encoded tile payload or current accounting charge**, not measured heap usage, peak memory, latency, or compression ratio on real artwork. Candidate numbers include an assumed 16-byte per-tile record header; they exclude command indexes, checksums, allocator capacity, alignment and temporary buffers. The delta encodes each consecutive changed run with 8 bytes of start/count and 8 bytes per changed pixel (old/new ARGB); the snapshot candidate uses zlib level 1 on each present before/after full tile; the hybrid chooses the smaller of the two **per tile**. Current charge is the existing 524,800 bytes per touched tile; current retained pixel payload can differ, notably for an absent-before tile.

An adaptive hybrid is justified by these samples, not proven optimal. Real line art, textured brushes, alpha-heavy layers, photographs, erasing, fills and many-tile strokes require further measurements. The prototype is an encoding-size experiment, not a production encoder and not a benchmark of process memory or responsiveness. zlib is a reference codec, not an approved dependency or final codec choice. Data must be encoded using an explicitly defined byte order in production.

## Components and ownership

```text
QML / CanvasViewport: begin, samples, end, cancel; UndoStack facade
  -> StrokeTransaction (single active document edit)
      -> BrushStroke / SparseTileStore (same pixel semantics)
      -> DocumentResourceManager (reservations + accounting)
      -> HistoryRecorder (tentative before state, final state)
  -> HistoryController (ordered commands, cursor, operation state)
      -> HistoryStore interface -> RAM store -> later bounded disk tier
      -> atomic RestoreTransaction -> document tile store
  -> Viewport invalidation/cache (evictable)
```

The document owns the controller and budget manager; layers/stores reference that manager and have stable document-unique layer IDs that are not row numbers or raw pointers. Workspace binds the active document's facade. Every command has a stable ID, layer ID, ordered tile records, before/after existence bits, encoding version, lengths and integrity check. Bounds, tile geometry, premultiplication and record-size limits must be validated before replay. A tile delta must distinguish absent from present; zero-pixel payload must not accidentally turn an absent tile into a present empty tile. The existing store's invariant says allocated tiles contain a nonzero value, so present-but-all-zero is invalid unless that invariant changes explicitly.

### HistoryStore boundary

An internal `HistoryStore` exposes opaque immutable `RecordHandle`s and operations conceptually `reserve(worstCase)`, `publish(records, reservation)`, `read(handle)`, `release(handle)`, `prefetch`, and `status`. Reservations are RAII tokens with explicit byte/category accounting. Publication either transfers ownership of a complete immutable command or leaves the old state unchanged. Handles do not depend on a RAM address or filesystem offset. All existing public QML operations—`Workspace.history.undo()`, `redo()`, `canUndo`, `canRedo` and `stackChanged`—remain the facade; storage location and encoding are not exposed to callers.

Cold undo/redo becomes asynchronous internally: emit a `busy`/progress state, prevent concurrent edits and cursor changes, read and validate on a worker, then commit on the document/UI thread. Repeated Undo/Redo input is serialized with a bounded request queue and clear enabled-state behavior; no blocking synchronous disk read on the UI thread. Existing void invocations stay source-compatible but callers and tests must stop assuming completion before the signal; document this behavioral change. Prefetch adjacent commands within a bounded cache. Commands and indexes may themselves be paged/segmented; merely spilling payload while keeping one large heap object per stroke forever is not sufficient for long sessions.

## Stroke transaction and allocation safety

Because a user can extend a stroke into previously unknown tiles, its final memory cannot be reserved at pen-down. Reservation is incremental **before each tile's first modification**:

1. Begin a transaction and capture current history cursor, layer identity, brush and view state; block concurrent destructive edits. An unchanged stroke needs no command.
2. Before a dab modifies a new tile, reserve worst-case capacity for (a) original tile/version and rollback ownership, (b) mutable working tile and final replayable state, (c) dirty/invalidation and map/node bookkeeping, (d) command metadata and durable/admitted record capacity, and (e) replay staging/scratch described below. Actual allocations are performed, not just arithmetic quotas. For new tiles reserve insertion nodes and existence metadata; for reclaimed tiles retain the original node/version until transaction outcome. Use stable immutable tile versions/copy-on-write or ownership-swappable nodes so rollback can restore prior tile pointers and existence **without allocation**. Resource tokens include allocator capacities and conservative metadata; arithmetic is overflow-checked.
3. Only after all needed reservations/allocations for that tile succeed may writes be visible on its tentative working version. Track original pixels once and final values; avoid a per-pixel allocation. If a dab enters an unreserved tile and allocation fails after earlier dabs, abort the **entire** stroke using the preallocated ownership/rollback path. Do not assume the current `restoreTiles` is rollback-safe under memory exhaustion: it allocates staged buffers and can fail.
4. At release, finalize a complete lossless record. The admission representation must already have a preallocated worst-case fallback—e.g. full before/after buffers—so failure to allocate a smaller adaptive encoding or a compression workspace cannot invalidate the stroke. Encode/compact immediately only within a bounded budget or in the background. Compare byte sizes and select runs or lossless compressed snapshots per tile; if compression or its verification fails, retain the safe raw fallback. Never rely on the compressor producing a smaller result. Capture final existence independently of values. Discard genuinely unchanged tiles; a completely unchanged stroke neither adds history nor drops redo.
5. Prepare the complete history command, record-handle table, undo cursor transition, updated tile versions and notifications before publication. Publish under a document-thread transaction with no fallible allocations or I/O in its critical section. Only then report the stroke accepted and release temporary rollback state. On any pre-publication failure or interrupted input, swap back originals with preallocated nodes, restore dirty/invalidation state or issue already-reserved invalidations, preserve the original cursor and redo branch, and report a rejected stroke. This prevents partial/unrecorded paint. Notification/render caches may be invalidated conservatively; loss of a repaint must never alter artwork.

**Replay headroom:** an accepted command must not rely on later unreserved heap allocations to restore it. Keep a reusable, physically allocated replay/rollback reserve sized to the largest admitted command's worst-case staged replacement plus metadata, with equivalent bounded disk-read/codec workspace. Before accepting a larger command, grow this reserve successfully; never reclaim it while commands that need it remain. Undo/redo reads and validates an entire command into reserved storage, builds all replacement versions and map nodes, then atomically swaps the full set and moves the cursor. If read/validation fails, free/reuse staging and leave both artwork and cursor unchanged. Full-command staging can be large; the budget must count it and a stroke that cannot secure it must be rejected before commit. A chunked implementation may reduce peak only if it supplies equivalent rollback ownership and proves atomicity under every injected failure; do not commit tile-by-tile without that proof. Compression, eviction and renderer allocations cannot borrow this reserve.

Physical reservation protects against ordinary allocator failures but cannot defeat OS process termination, hardware failure, filesystem corruption, or externally removed swap storage. The design promises exact replay on successful validated I/O, not guaranteed availability in those cases. If preserving all previously accepted commands cannot be assured, stop accepting edits and offer recovery rather than silently losing history.

## Shared, dynamic resource manager

One manager per document covers all layers and all history for that document. A process-level coordinator is also required when multiple documents exist, so separate document budgets cannot overcommit the same machine. Replace the existing isolated 256 MiB per-layer ceiling only after all call sites and file loading participate.

Track separately, with current, reserved, peak and reclaimable counters:

* Artwork tiles and their node/capacity overhead across layers, including tentative versions and rollback-retained nodes.
* Hot, cold, redo and in-flight history; shared immutable versions must be charged once with ownership/refcounts.
* Replay reserve, compression/decompression scratch, spill queues and indexes; shared buffers counted once.
* Compositor cache, viewport frames and temporary composites; cache evictions happen first, but pinned frames and GPU/Qt allocations need their own estimates.
* Save/open staging, parsed file buffers and candidate document memory, including simultaneous old/new documents during Open/New.
* Process memory outside managed pools and OS available memory are observed with platform APIs where available, not assumed equal to accounting totals. Allocator overhead, RSS/private commit, driver allocations and OS pressure are separate telemetry with explicit uncertainty; budget accounting is not an exact process-wide memory guarantee.

Preferences specify a configurable RAM target or OS-aware automatic policy, free-memory headroom, bounded history storage location/quota and disk-free safety margin; show derived capacity, actual use, pressure and quota. Avoid inventing an undo step cap. Automatic defaults should be chosen from profiling low-end machines; document their rationale and allow adjustment. Keep a non-borrowable emergency reserve for rollback, error reporting and replay. Disk quota accounting must include pending writes and indexes; filesystem free space can change outside the app, so a reservation is not a guarantee of future writes. Decreasing a preference below committed usage does not silently delete anything: reject/defer the change and explain the required action.

## RAM/disk tier and failure behavior

Design the interface now, but ship disk tier as a separately gated milestone rather than claiming RAM-only history already satisfies effectively unrestricted sessions. Cold immutable records can be compressed and written asynchronously to a versioned, checksummed session store. Keep the hot copy and its reservation until a complete write is flushed and verified, then atomically publish the disk handle. A writer failure leaves the RAM copy intact. Bound queues, concurrency, index and prefetch memory; pause admission with a clear status if the queue or both tiers are full. A slow disk may make cold undo slower; it must not freeze pointer handling or reorder commands.

Use secure per-user permissions, unpredictable session paths, clear privacy guidance, and cleanup on normal exit; offer cleanup of stale files after crashes. Encryption and multi-process coordination are separate design decisions, not implied by a temporary file. Validate checksums and lengths on read; detect truncation, corruption, read-only paths, quotas, network removal and external file deletion. On corruption or inaccessible media, do not change the canvas/cursor, preserve other records and offer Retry / choose storage / save artwork / explicitly discard affected history. During an active stroke, inability to reserve safely rejects and rolls back that stroke. Keep history until user explicitly confirms discard; saving artwork does not itself clear history. Disk storage is session cache, not a durable undo archive, unless a separate recovery design is approved.

## Migration and compatibility

1. **Instrumentation only:** propagate typed resource failures, measure actual allocations and peaks, add counters, stress/fault-injection tests and a no-op diagnostic UI. Preserve legacy behavior while observing it; identify the user's actual trigger where reproducible.
2. **Budget foundation:** introduce document/process manager behind existing stores, accounting and reservations for current behavior. Add transactional store primitives and no-allocation rollback while retaining current history representation. Make layer removal/document replacement respect the stated history-loss policy. Prove save/open and all existing workflows before enabling the manager by default.
3. **RAM hybrid:** implement record interface, pre-reserved replay/rollback, exact adaptive encoding and a reference old-snapshot implementation for differential tests. Replace only after test and performance gates pass; keep a temporary feature flag / rollback path. The 64 MiB cap is replaced by managed resources, not simply increased. No old `.koma` migration is needed: current undo history is session-only and reopening already starts a new session. Never reinterpret an in-memory legacy command as the new format.
4. **Disk tier and UI:** implement, fault-test and security-review spill/prefetch, settings, telemetry, user warnings and explicit redo/history-loss choices. Test Windows on slow disks and real tablet hardware before declaring the unrestricted-session goal achieved.
5. **Broaden command coverage:** integrate future edits, layer deletion and other operations into the same transactional history. Until then, explicitly disclose unsupported actions and do not claim complete-session undo for them.

Risks include increased in-flight memory (whole-tile safe fallback and replay reserve), UI latency from encoding or branch prompts, Qt async API assumptions, disk data privacy, stale handles after layer deletion, and save/open peak allocations. `.koma` pixels, alpha, metadata and on-disk format must remain compatible; the document loader must use shared budget reservations without accidentally rejecting valid files due to double counting. New Project, drawing, Save and Open remain regression gates. No performance claim should be made until measured on target hardware.

## Required tests, measurements and release gates

* **Correctness:** seeded and property-based differential testing against exact full-tile reference states after every stroke, undo and redo, checking every pixel and existence bit. Cover alpha, premultiplication, empty/no-op, repeated writes, multiple layers, tile boundaries/edge tiles, creation, erasing/reclamation, cancellation and replacement. Test divergent edits, explicit redo decisions and unsupported layer actions.
* **Long sessions:** at least thousands to tens of thousands of mixed strokes, including rapid many-tile input on large canvases; repeated full traversal of retained undo/redo, save/reopen and continued editing. Verify no command loss or cursor drift and bounded RAM, metadata, disk, queue and reserve usage. Also exercise command-count/offset overflow.
* **Deterministic fault injection:** fail each allocation/reservation/node creation, compression, checksum, disk write/flush/read, prefetch, publication and notification boundary. Compare all artwork, tile states, cursor, redo and counters before/after. Exercise interrupted strokes, full disk, quota changes, slow or removed storage, damaged records and failure to grow replay reserve. Validate rollback without further allocations and restoration after every failure point.
* **Performance:** report current versus new p50/p95/p99 input-to-render latency, stroke finish latency, cold/hot undo latency, throughput, UI event-loop stalls, peak process private bytes/RSS, GPU where observable, per-category budget/actual usage, disk size and write amplification. Use realistic imported artwork plus synthetic blank, flat, noisy and sparse inputs; vary brush size, opacity, length, zoom and layer count. Benchmark on a low-end Windows PC, SSD and slow/full storage. Agree measurable budgets after collecting baseline; do not use synthetic payload sizes as proof of speed or RAM savings.
* **Integration:** preserve existing New Project, viewport, brush, undo, file and QML tests; add actual pointer-driven interruption/retry and asynchronous Undo/Redo behavior. Check saving/reopening exact pixels after extensive work. Verify packaged Windows app manually with mouse and pen; CI alone is not acceptance.
